# 轻语：可行性、技术路线与实验方案

2026-10-10。状态：**0.2.8 已实现可关闭的轻语候选、诊断与实验入口；真人轻声录音和云端质量对照尚未执行**。当前交付与证据见 [0.2.8 实施记录](soft-voice-0.2.8.md)。下文代码事实与阶段建议保留为实施前基线。

源码核对基线：本机桌面 0.2.7／前端 0.4.6，HEAD `df811f802f09402e639582ca0d77bf604eb27a81`，另有未提交工作树改动。后续实验必须冻结实际源码／可执行文件哈希，不能只用 HEAD 代表被测版本。

用户已明确：第一版针对**轻声说话但仍有正常音调**，不将纯气声耳语列为承诺支持的场景。

## 产品定位

“轻语”是 SpeakMode 的全局采音偏好，对自动、轻整理、结构和个人 Mode 都生效；输出 Mode 仍只控制文本整理方式。目标是在安静或轻度背景噪声下，降低轻声口述的漏字、漏句与空结果，同时保持正常音量输入的质量和等待时间。

拟采用“设置 → 音频 → 轻语增强”开关，说明为“适合安静环境下轻声输入”。先默认关闭，实验达到门槛后提供用户启用。沿用右 Alt 开始／结束、长停顿继续录音与现有输入流程。浮层不增加一套选择面板，开启状态可用小标记表达。

应用内部调整音频，不自动修改系统麦克风音量。可后续提供一次短校准，但不要求每次口述先校准。配置在会话开始时冻结；录音中修改设置只对下一次生效。首版暂不按设备保存个性化校准：当前 CPAL 设备 ID 基于名称，不是稳定 WASAPI endpoint ID。

因此，现阶段不能把轻声失败归因于“本地 VAD 切掉了声音”。可能来源包括电平过低、语音相对底噪过弱、设备自身处理、通道均值损失或服务端识别／VAD；需要采样证据区分。

多通道中一路为空时平均会降低幅度、反相通道可能抵消，是数学上可验证的风险；尚未证明用户当前设备存在此问题。先加分通道元数据，不能默认选择最响声道，因为最响的也可能是噪声。

## 推荐实施顺序

### 第一阶段：可测量的保守增强

建议链路：

```text
WASAPI → 既有混音/重采样 → 16k浮点质量测量
       → 可旁路的轻语增益与限幅 → PCM16/100ms帧
       → 现有ASR → 现有Mode整理 → 成稿和输入
```

1. 增加输入和处理后 RMS/dBFS、峰值、削波比例、增益分布、处理耗时及每通道能量等聚合统计。噪声估计与“是否有人说话”必须标为估计，不能把普通低 RMS 直接视为无人声。
2. 先比较纯旁路、受限固定增益、受限自适应增益三个实验臂。自适应候选要限制底噪放大和最大增益，平滑增益变化，遇突然正常音量快速收回，使用峰值保护而不是直接硬截断。
3. 静音时不持续追高增益，不增加硬噪声门；语音置信度只辅助调节增益，不据此删掉 PCM。轻声第一字也必须保留。
4. 初始可用 +6/+12dB 作为开发集探索范围，上限、目标电平、attack/release 均为待测参数。验证集开始前只冻结一套固定增益与一套自适应参数；不在看到验证结果后继续调同一批数据。

自动增益并不等于识别率提高。线性放大会同时放大语音和底噪，不能改善原本的信噪比；模型若已经做了归一化，也可能几乎不获益。因此效果以转写结果为准。WebRTC AGC2 源码具有噪声上限、增益变化限制和置信度保护，可作为参考实现与候选基线，但其语音置信度驱动策略仍需真实轻声验证。[WebRTC AGC2](https://chromium.googlesource.com/external/webrtc/+/master/modules/audio_processing/agc2/adaptive_digital_gain_controller.cc)

### 第二阶段：只在失败证据支持时加入降噪或调整 VAD

| 候选 | 适合验证的问题 | 取舍 |
| --- | --- | --- |
| Rust 小型增益／限幅模块 | 低电平但语音仍清晰 | 最小接入候选；可直接复用现有16k浮点数据；不宣称具备成熟语音增强模型的全部能力 |
| WebRTC Audio Processing／AGC2 | 需要更成熟的电平与噪声约束基线 | 有现成机制，但 C++ 构建／FFI、实时预算和语音置信度都要验证 |
| RNNoise | 风扇／空调等背景噪声下，保守增益仍无效 | 上游示例是48k单声道PCM；需考虑放在降采样前，不能把16k转48k当作恢复细节；单独检验是否损失轻声辅音 |
| DeepFilterNet | 复杂噪声下再做增强候选 | 有Rust相关实现和48k处理入口；引入模型、计算和时延，先离线评估再决定Windows实时接入 |

RNNoise 和 DeepFilterNet 是候选方案，官方项目存在不代表已经证明适合本产品的低声中文输入。[RNNoise](https://github.com/xiph/rnnoise)，[DeepFilterNet](https://github.com/Rikorose/DeepFilterNet)

当前 Qwen3 阈值已为0.0。官方允许 [-1,1]，所以技术上还可试负值，但它会同时提高噪声触发风险；应将0.0与一个小步负值作为独立实验，而非直接拉到最低。Manual 模式需要客户端 commit，会改变分段和字幕到达方式，不宜作为第一步。Audio3.1 的 vad_model／speech_noise_threshold 是不同协议参数，不能把 Qwen3 字段原样复用。[Qwen3客户端事件](https://help.aliyun.com/zh/model-studio/qwen-asr-realtime-client-events)，[Audio3.1客户端事件](https://help.aliyun.com/zh/model-studio/qwen-audio-asr-streaming-client-events)

如果进入应用的 PCM 已被设备驱动处理而丢失语音细节，应用内增益不能还原。Windows 支持 RAW／非RAW采音和不同音频处理类别，但实际支持取决于驱动；只有采音对照证明有问题时才评估专门 WASAPI 路径，不假定所有设备都能关闭全部处理。[Microsoft音频处理模式](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/audio-signal-processing-modes)

## 工程边界

- 新增独立 `AudioInputProfile`（建议 Standard／SoftVoice），旧配置默认 Standard；同步 Rust Preferences、存储兼容、前端 contracts 和音频设置。
- 新建 `platform/audio_conditioner.rs`，在 `audio.rs` 的重采样浮点帧到 PCM16 量化之间接入。放在采音工作线程，设备实时 callback 不做模型推理、额外锁等待或大块分配。
- 10/20ms 内部 DSP 子帧可以保留100ms网络封装；处理须维持样本数、帧序、padding 和停止时尾音 drain。若算法引入 lookahead，要明确报告延迟并排空，不能悄悄截掉尾字。
- 增强后的 PCM 进入既有重试缓存，重放时不得再次施加增益。日常不新增双份原始录音留存；原始/增强对照只在明确的实验采集入口进行。
- 增加处理配置版本与聚合统计，沿用诊断白名单，不把正文、PCM或Key写入日常诊断。
- 波形可改进低电平可见性，但必须仍反映真实收音；“波形会动”和“识别更准”分别验证。

## 实验设计：先回答增量来自哪里

现有 `scripts/voice-quality-lab.py` 可复用冻结素材、dev/test隔离、CER/WER、关键事实盲评和失败保留分母。`examples/voice_lab.rs` 使用生产ASR进行100ms实速PCM回放，但当前绕过采音前处理，必须显式接入同一处理模块，才是在测试候选链路。

第一轮建议3名说话人 × 6段内容 × 正常／轻声两种音量 = **36段真人语音**，另加12段无人讲话负例。1人用于开发，另外2人参数冻结后测试。短段8–15秒为主，另保留长停顿后续说的边界素材；分别标注实际说出内容，而非把提示稿自动当成参考。

内容覆盖否定、条件、金额／日期改口、中英混合专名、句尾渐轻、停顿续说。首轮固定一种实际麦克风与口距，候选胜出后再加入笔记本／耳机麦克风和轻度环境噪声。第一轮是试点，不外推所有用户或纯耳语。

同一条原始录音进入各臂，不让用户重新说一遍当对照。尽量保留设备可提供的原始浮点或高精度实验音频，各臂统一处理后编码PCM16；如果只保存了极弱PCM16，已量化丢失的细节不能补回。人工降低普通录音音量只用于工程回归，因为它连原来的底噪也一起降低，不能代替真人轻声。

先测ASR原稿，固定模型、地域、词典、语言和分段；候选冻结后再接同样的Mode整理检验最终文本。三个臂、48素材总计144次ASR为基础矩阵；追加素材／模型对照需另外登记。保留现有单批≤18次请求、≤600秒源音频的限制，明确总批次而不是扩大预算。当前未执行这些请求。

现有评分器要求非空逐字稿和关键事实，需要新增无人声样本类型。静音的CER分母为零，应用“出字片段比例／每分钟误输出字数”；当前首字幕计时从任务开始算，只有补发声起点标注后才能声称“说话到字幕”。

| 验证内容 | 指标 | 拟定门槛，尚无测量结果 |
| --- | --- | --- |
| 轻声是否听得更清 | 中文CER／英文WER、空结果、整句及首尾漏字 | 以轻声CER相对降低约20%作为试点目标，同时报告绝对错误数／百分点；基线很低时不夸大相对值 |
| 是否引入语义错误 | 否定、条件、数值/单位、改口、专名分别核对 | 新增关键事实错误阻止默认推广 |
| 正常声音是否退化 | 正常音量CER与削波 | 初始护栏为CER不恶化超过1个百分点，同时逐条检查严重错误 |
| 是否把底噪当说话 | 纯静音、风扇、键盘、呼吸/衣物摩擦的误出字 | 不得因轻语增强而增加可交付的虚假语句；不能对静音算CER |
| 是否仍然顺畅 | DSP单独耗时、首字幕、停止→ASR/成稿 | 候选额外处理与等待以100ms内为初始预算；分开报告本地耗时和网络分布 |
| 是否丢音或重复处理 | 样本/帧计数守恒、完整drain、停止/取消/重试 | 不删停顿，不重复增强，不因低电平报告断供 |

这些是拟定产品门槛，不是行业标准或已有成绩。小样本先报告配对差值、人数、范围和失败案例；正式推广再扩大说话人、设备及噪声覆盖。

## 下一步的具体交付

1. 先补质量元数据、共享可旁路处理器和空语音评测类型，建立固定增益／自适应增益实验入口。
2. 用真人正常／轻声配对音频筛选，未达质量与噪声护栏时保持现有默认；有证据再单独比较降噪、VAD或模型。
3. 胜出后接入设置开关、持久化、会话快照、状态提示和重试语义，再做完整Windows实际口述/输入验收。

初次调研仅添加方案文档。用户随后确认定位，0.2.8 接入实验性增强开关（默认关闭），并补共享处理器、持久化、重试和纯静音评测支持；没有修改用户资料或默认模型。真实质量门槛仍待验证，不能将工程测试视为识别率提升。
