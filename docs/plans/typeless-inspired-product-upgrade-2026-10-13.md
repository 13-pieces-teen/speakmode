# SpeakMode：借鉴 Typeless 的听写体验升级

日期：2026-10-13。状态：产品路线已调整，以下新增能力尚未实现或验证。核对源码为 `a6858f3`，桌面版本 0.2.20；保留当前首页与词典界面改动。

用户明确要求根据 Typeless 的优点优化 SpeakMode，工程范围应由体验目标决定。本路线接续[原实施计划](typeless-rea-implementation-2026-10-13.md)：已完成的期限传递、Helper 调查和输入探针继续作为基础；后续优先级由完整听写体验确定。

## 产品目标

用户在正在使用的应用里自然说话，得到意思完整、表达顺畅、格式合适的文本；结束后少等待、少切换界面，失败后能继续完成这次输入。

主要指标是**一次口述直接可用率**：内容与意图正确、表达可读、格式适合任务，并且已在受控目标位置观察到正确文本，无须人工修改。分别记录人工修改量、完成任务的时间、停止到实际出现文字的时间，以及识别稿回退率。无法观察宿主时，不计为已确认输入成功。

## 第一阶段：场景感知的自然成稿

这是下一个完整产品目标。交付同时覆盖场景输入、整理策略、用户控制和同源效果比较；Word 超时定位作为其中的原生兼容工作。

### 场景和用户偏好进入 Auto

- 增加会话级写作场景快照，包含任务类型、表达偏好、上下文来源与版本。聊天、文档、技术输入和通用场景分别提供自然句子、段落、列表及标识符保护等表达规则。
- 优先支持本地应用/控件能力与用户设定的应用偏好。单靠浏览器进程名无法区分聊天与文档；证据不足时使用通用场景，不猜测任务。
- 将“使用光标附近文本”设计为明确可选能力，限定为当前可编辑控件的有限选区及前后文。它用于接续句子、术语提示和格式适配；不得作为补写人物、金额、结论等事实的来源。范围、开关和应用排除项在设置中清楚呈现。
- 显式选择的 Mode 和本次个人规则优先于自动场景。已有“纠词并记住”继续使用；新增的是应用表达偏好及其会话应用，不能把已有词典功能算作新交付。

### 上下文与实际输入位置保持一致

- SpeakMode 允许录音中移动光标，实际交付位置仍以停止时目标为准。背景预取只用于降低等待；最终采用的上下文必须与停止时目标身份相符。
- 采集与录音/ASR 收尾并行，设置独立时间与长度上限。采集失败或来不及时，使用语音来源和显式 Mode 完成本次整理。
- 将来源、Mode、词典和场景快照一起冻结并绑定生成/复核任务。迟到的上下文不能改写已经生成或交付的结果。
- 宿主文本按不可信数据处理；其内容不能发起工具调用、改变系统规则或授权输入。诊断保留阶段、长度和失败原因，默认不写入宿主正文。

### 以成稿质量选择整理方案

- 保留事实和说话意图，比较更自然的接句、废弃起句处理、最终改口表达、段落组织和列表排版。数字归属、否定、条件、主观态度、引语和代码需要分别核对。
- 在现有生成请求中传入场景，不固定增加一次云端场景分类调用。允许调整提示、数据结构和复核流程；调用次数、质量与等待时间一起比较。
- 建立同一语音内容在聊天、文档和技术场景下的预期输出；也覆盖明确 Mode 覆盖自动场景、录音中换应用、局部上下文矛盾、无上下文和上下文超时。
- 先比较现有版本、仅改进整理的候选、加入场景的候选，区分各项改动的实际收益。开发素材与独立预留素材分开；模型放行率仅作诊断。

第一阶段验收：相同输入下人工修改量下降、场景排版更合适，并报告完整可用率与实际等待；事实误改、换目标误输入和取消后输入均不能通过。只改善已有失败例而没有独立预留收益的方案继续迭代。预留比较和真人音频尚未执行。

## 第二阶段：连续听写和跨应用交付

在第一阶段的共同目标快照上建设输入能力层，覆盖原生控件、浏览器、Word、聊天框和代码编辑器。能力判断决定普通文本、换行/列表以及可选富文本的交付方式；富文本支持需单独验证，不能根据 Typeless 导出名就宣称兼容。

录音交互支持点按切换与按住说话，并明确长口述锁定、松键结束及 Esc 取消的行为。保持原有点按习惯；新增手势处理早松键、麦克风启动中取消、快速连续口述和组合键，避免录音浮层抢走目标焦点。

剪贴板交付需要考虑用户原内容及等待期间的新复制操作。恢复前检查本次写入的所有权；已发出输入但结果未知时保留单次交付约束。目标变化时让成稿就近可取，恢复操作沿用浮层和记录中的现有入口。

验收按完整任务检查操作次数、首个录音反馈、停止到文字显示、宿主最终内容、剪贴板干扰和连续会话成功率。Word 超时及飞书/VS Code 未测项纳入这一阶段，不以修复一个异常作为整个体验升级完成。

## 第三阶段：快速恢复和弱网接续

先完成文件识别的质量与时延比较，再把更快的识别路径接入显式重试。已有三段合成音频中，恢复时间中位数为 20.815→0.863 秒，脚本 CER 为 6.67%→8.00%；目前仍是提速潜力，不能作为质量等价结论。补齐真人、长音频、术语、否定和尾句覆盖，并使用独立预留素材。

通过后，再实现有条件启动一次后备的会话恢复：主路径停滞达到实测阈值时启动，两个分支共享会话身份和一次交付仲裁，首先完成且完整有效的结果才能胜出；取消、新录音和过期均使旧结果失效。测量额外调用成本，避免把客户端取消视为服务端停止计费。

验收看无需重新口述的恢复率、恢复总时长、完整性、术语质量及额外请求数。原 ASR 实验总上限 52 次、已使用 6 次；新路线不自动追加云端实验或扩大该预算。

## REA 的后续工作顺序

1. **上下文如何支持场景化输出**：追 `collectFullContext`、`replace_audio_context`、`ContextHelper.dll` 与黑名单分支，明确字段、读取范围、时机、超时、焦点变化和失败处理。产出可独立实现的输入契约。
2. **怎样自然地开始与结束口述**：还原点按/长按/免手持的状态转移及初始化期间松键分支，用同样的用户动作验证 SpeakMode。
3. **如何形成完整成稿并进入应用**：结合运行时记录解释停止到转写、整理与插入的时间，并追纯文本/富文本选择条件。
4. **怎样在弱网下继续完成**：确认后备触发、有效结果仲裁、取消、历史重试与是否重新输入的具体语义。

已完成的 Input Helper 调查继续复用。服务端提示、模型与质量仍需通过自己的对照实验决定；不把客户端静态机制当作效果证明。REA 的调查结论转化为 SpeakMode 的体验、输入契约和验收用例，不将厂商反编译代码带入产品。

## 交付组织

以三个体验阶段组织后续工作，阶段内部允许因会话上下文、整理协议、原生能力或状态机需要进行重构。PR 按可审查依赖拆分，阶段完成由用户效果决定。

第一阶段的具体开发入口：定义会话场景快照和停止时目标绑定；实现本地应用表达偏好与 Auto 场景策略；加入可选局部文本上下文；完成同源成稿和完整输入比较。第二、三阶段继承相同的来源、取消、恢复和一次性交付约束。

本次只调整产品路线和工作顺序，没有启用上下文读取、新手势、自动后备，没有进行新云端调用或发布新版本。已完成的 A/B/C 证据仍保留在原实施计划中。
