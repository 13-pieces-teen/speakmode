# SpeakMode：期限修复、输入与时序调查、文件恢复实验实施计划

日期：2026-10-13。状态：**计划已整理；A–C 均未执行**。核对基线为 `79b317f2ce5e723ab36c96c49c0cc83780df124f`，桌面 0.2.19 / 前端 0.4.18。计划对应用户选定顺序：“先修期限传递，再调查输入 Helper 和真实时序，然后做文件恢复实验”。版本号在实际交付时分配。

**A：先修复期限传递，形成一个可独立交付的增量。**

当前调用链中，协调器按源文长度设置 5/8/20 秒，生产 cloud 入口却仍传入固定 20 秒；内部据此决定是否剩余至少 1,400 ms 启动修复。外层会拦住迟到结果，但内部可能启动赶不上外层期限的请求。该问题应先用真实调用路径与本地假服务复现。

| 任务 | 实施内容 | 主要文件 |
| --- | --- | --- |
| A1：贯通 deadline | 在协调器选定预算时创建唯一 `tokio::time::Instant`，传入 cloud dispatcher、minimum/fluent/基线请求路径；下层不再重新起算 | `engine/session.rs`、`cloud/rewrite.rs`、`cloud/rewrite_minimum_pipeline.rs`、`cloud/rewrite_fluent_pipeline.rs` |
| A2：保留入口语义 | 增加接收绝对截止时间的内部入口；显式重试、历史候选、Mode 试用按各自原预算创建截止时间，避免所有入口误套初次口述的 5 秒 | 上述文件及实际调用点 |
| A3：修复请求准入 | 生成/复核/修复前和同步解析后检查同一截止；保留原 1,400 ms 修复余量，先校正时间来源，再用数据考虑调参 | minimum pipeline、共享 request helper |
| A4：最小诊断 | 增加生成、复核、修复、新复核的开始/结束、耗时、实际发起次数、固定结果码及修复开始时剩余预算 | `engine/diagnostics.rs`、cloud stage callback、诊断导出器 |
| A5：当前入口 | 校正工作区当前版本导航，保留旧交付记录；本版报告描述静态发现、复现、修复与实测范围 | 当前入口与新实验记录 |

现有 `request_content` 已接受绝对 deadline，可直接复用。pipeline 的实验 Trace 含草稿与复核内容，**不得把整个 Trace 导入生产诊断**；只投影固定标量和枚举，保持有界容量及正文过滤。

必须保留的行为：初次口述整理失败后才允许完整原稿保底；取消/会话失效不产生可交付文本；只取消整理子 token，不把正常原稿回退所需会话一起取消；同步解析后的迟到检查保留；自动输入仍由唯一许可仲裁；手动重试不恢复旧的自动输入资格。模型、提示、ASR、预算档位和 Mode 规则在 A 阶段维持当前配置，以便归因。

A 的关键验证：

- 在**协调器→生产 dispatcher→pipeline→本地 HTTP 假服务**整条路径复现预算差异，检查真实收到的请求数。只有 pipeline 单测无法覆盖本次问题。
- 短文 5 秒场景：让生成与首次复核累计消耗超过 3.6 秒，确认不足 1.4 秒时不发第三次修复请求；中、长文验证同一规则。可用受控时钟缩短测试，但覆盖真实时间类型及外层接口。
- 覆盖源文 400/401、800/801 字符边界、每个阶段取消、同步解析迟到、会话替换、来源/Mode/草稿失效。
- 确认超时原稿最多交付一次；取消不交付；手动重试不自动交付；新旧错误码都可被安全导出。
- 通过相关测试后跑一次 Windows 桌面库回归；诊断格式变化时同步运行 Python 导出器测试及 TypeScript 检查。只有修改了界面呈现才补相应浏览器检查。

**A 验收门槛：**上述行为检查全部通过；基线固定素材的原始输入及保护条件不变；预算内请求数量可解释。减少请求数是直接工程收益，真实等待或质量改善需要 B 的运行数据确认。A 可先形成独立候选包，不依赖 B/C 的实验成功。

**B1：调查 Input Helper，建立宿主证据。**

1. 核对 Typeless 安装版本、ASAR/DLL SHA；复用既有 first-party Evidence 与解码阅读副本。若安装已更新，另存新快照，不能沿用旧行号宣称新版本行为。
2. 检查实际 REA 版本、`doctor`、provider 及匹配的 Ghidra/JDK。Windows 原生支持仍为实验性，先完成最小只读 provider 检查，再分析 DLL。[REA Windows 文档](https://github.com/morluto/rea/blob/main/docs/windows-ghidra-p0.md)
3. 限定导出入口：`insertText`、`insertRichText`、`getCurrentInputState`、`getSelectedTextBySimulateCopyAsync`。记录输入方式、选择条件、锁、返回码、选区/焦点检查、结果确认与清理路径。
4. 核查 JS 层“返回 1 后等 500 ms”的实际作用，保留未知项；不将其当作宿主已接受输入的证明。
5. 用受控测试文本验证 SpeakMode 当前行为，再根据可复现差异提出适配。拟议的新输入策略必须在原策略尚未派发前选定；已派发但未确认时不能自动补发。

宿主基础矩阵为 6 组 × 5 场景，共 30 格：Windows Edit/RichEdit、浏览器 textarea、contenteditable、Word、飞书输入框、VS Code；场景为普通中英/emoji、多行长文、选区替换、等待中换窗、注入前取消。复用已有只读/密码/不可编辑/权限检查；未安装或无法独立观察的宿主记为未测。

先用现有 `owned_delivery_probe.rs`、`owned-browser-delivery-qa.py` 和本机 `run-owned-native-delivery.py` 建立可控基线。测试回读与生产自动回读是两个范围：本轮允许在测试宿主核对结果，生产是否增加回读需要依据 B1 单独设计。

**B1 交付：**导出函数与调用路径表、每格结果/复现步骤、明确的适配建议清单。若没有发现可验证收益，交付调查结论即可，不为模仿竞品增加输入路径。

**B2：记录真实等待，决定后续性能工作。**

第一轮拟固定 12 段已核对音频，10/30/60 秒各 4 段；同一音频用于两款产品，分别在正常网络与受控慢网测试，共最多 48 次产品会话。调用数另按实际请求记录：一次会话不等于一次模型请求。已有预留集仍保持独立，不用于反复调参。

| 事件 | SpeakMode 观测 | Typeless 观测 |
| --- | --- | --- |
| 停止意图与尾段排空 | 原生单调时钟与音频计数 | 已暴露的录音停止事件/运行日志；不可见则空缺 |
| 最终音频发送、ASR 最终结果 | 已有 ASR 诊断 | 网络/IPC 中确实可见的相应事件，不据客户端发送推定服务端收到 |
| 生成、复核、修复 | A 新增阶段标量 | `refine_completed` 等客户端可见结果；服务端内部调用保持未知 |
| 后备触发与取消 | 当前路径及实验状态 | `startRefineRace`、`sendFallbackEvent`、audioId 对齐的实际事件 |
| 派发与宿主出现文字 | 原生回执＋受控宿主观察 | Helper 调用/结果＋受控宿主观察 |

每个产品内部用同一单调时钟求间隔；跨进程事件建立可核对的关联和时钟映射，不能直接相减不同进程的 `performance.now()`。跨产品比较各自相同定义的时长，不比较绝对时间戳。相同音频通过受控输入路径送入，记录设备/编码和静音起点，避免将文件直传与真人麦克风链路混为一组。

优先使用可连接的被动观察、已有日志与完整网络证据；REA 主动 Electron 场景会拦截部分系统集成效果，不能单靠该场景判定跨应用粘贴成功。[Electron 观察边界](https://github.com/morluto/rea/blob/main/docs/electron-observation.md)

**B2 交付：**停止→最终 ASR→生成→核对/修复→派发→宿主显示的时间线，按长度/网络/结果类型分组的样本量、中位数和尾部值。小样本 P95 仅作初筛。现有“≤30 秒口述停止到成稿 P95 ≤5 秒”仍是待验证目标，不能用 A 的 5 秒整理预算冒充达到。

B 后的决策：若耗时主要在 ASR 收尾或失败重放，推进 C；若主要在整理，形成压缩串行调用的独立候选，保留质量检查；若主要在宿主派发，先按 B1 的最小适配修复。文件恢复成本已能独立确认时，可以继续 C，不必等待不相关的原生未知项。

**C：先做文件识别实验，通过后再接入显式重试。**

本阶段比较“已有完整 PCM 缓存按实时速度重放”和“完整音频文件识别”。不通过删掉实时重放 sleep 取得表面加速。当前恢复槽、原有约 30 分钟期限和 `CreationReason::Retry` 的不自动输入行为延续。

| 子任务 | 实施方案 | 产物 |
| --- | --- | --- |
| C1：接口预检 | 先核对当前地域、Key 所属接口、文件格式、长度/体积、词典与完成语义；最多 4 次合成音频预检 | 锁定单个候选、协议说明、可测范围 |
| C2：诊断适配器 | 新增隔离的文件 ASR adapter/诊断入口，读取显式测试音频；暂不加入默认实时模型选择 | 独立可复现实验工具 |
| C3：固定配对 | 24 段音频，两臂各一次；12 开发＋12 预留，10/30/60/180 秒每档 6 段；两臂顺序交错 | 最多 48 次识别请求及完整失败记录 |
| C4：决策 | 先冻结开发结果与参数，再运行预留集；识别质量、恢复时间与成本一起评估 | 接入/继续实验/停止结论 |
| C5：条件接入 | 只有 C4 通过才加入显式“重试识别”；仍需本地生命周期与异常验证 | 小范围候选实现及验收记录 |

候选优先核对 `qwen3-asr-flash` 文件路径；官方当前列出 HTTP、5 分钟/10 MB 限制。目录中已有 `qwen-audio-3.1-asr-flash` 文件模型占位，但 `implemented=false`，不能简单打开开关就宣称支持。若首选在目标地域不可用，记录原因后在 C1 选定一个候选，不在每个失败样例后更换模型。[官方模型范围](https://help.aliyun.com/zh/model-studio/asr-model/)、[当前模型目录](../../app/src-tauri/src/cloud/models.rs)。

实验请求上限拟为 **52 次 ASR 请求：4 次预检＋48 次固定比较**，不调用整理模型，以便单独衡量识别恢复。该预算是未来执行方案，本轮没有消费这些请求。取消、网络错误、畸形响应、空音频及长度/体积边界主要用本地假服务验证；超过候选范围的录音保留现有恢复路径，不截断、不隐式切块。

适配器必须记录实际 provider/model/adapterVersion，不能仍写入 realtime 型号。只有收到完整成功结果才创建 complete 来源；无分片/时间戳的响应可以形成有序的单个最终来源项，不伪造时间戳或借用旧 attempt 的 sourceRefs。冻结本次语言、词典与音频身份；模型不支持相同词典能力时必须在结果中体现。

正式接入前验证：新 generation/attempt 与取消所有权正确；恢复槽过期不延长；新录音、删除、退出、取消和晚到响应不复活旧结果；错误模型/空结果/超限不标为成功；结果不触发原目标的自动输入；失败也不暗中追加第二个云端重试。

**C 的预登记选择标准，均为目标而非已测结果：**

- 预留集总体恢复时间中位数至少降低 30%；60/180 秒组的尾部等待不比实时重放差，同时报告每条实际值。
- 完整性通过，关键事实逐项核对：尾句、数字/对象归属、否定和术语不出现新增严重错误；有参考文本时报告 CER/WER，不能只看输出长度。
- 每条成功或失败都计入结果；失败不能用更换素材或无限重试替代。12 条预留样本只支持下一轮有限接入判断。
- 请求量、费用口径与取消结果清楚；UI 显式恢复成功后仍由用户决定复制，自动输入次数为零。

未通过时保留完整实验和现行恢复，不放宽来源完整性换取速度。若速度收益通过但术语质量退步，列入后续候选，不直接推广。
