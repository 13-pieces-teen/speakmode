# SpeakMode 0.2.22 场景感知自然成稿：实现与实验记录

日期：2026-10-15。版本：桌面 0.2.22 / 前端 0.4.21。范围：场合与输入位置感知的可试用升级，实际模型收益及未覆盖范围分别记录。

本轮要改变的具体判断是：用户能否按正在完成的事情选择成稿场合，并利用当前输入框的有限上下文，得到事实完整、组织自然、适合直接使用的文字。实现已经覆盖场合入口、输入上下文采集和云端生成/复核协议；v1/v2 的合成文本实验发现了段落组织及口述请求遗漏，因此继续修订为 v3。本文不把协议接受、测试代码存在或静态实现当作真人使用效果。

## 1. 产品入口与处理原则

主要入口从整理强度转为使用场合：**自动、聊天消息、文档写作、邮件沟通、技术沟通**，并保留自定义场合。主界面、录音面板、设置与历史重新整理共享场合定义。已有“轻整理”“结构”及个人规则保持兼容；手动场合和个人规则优先。

| 入口 | 期望行为 |
| --- | --- |
| 自动 | 综合口述目的、可用输入框提示和应用匹配，保守判断用途；无法判断时按口述顺序形成自然段。 |
| 聊天消息 | 保留原有语气、条件和必要信息。聊天框中的长篇自我介绍仍按真实主题组织，不压成单段。 |
| 文档写作 | 形成连贯句子与主题段落；真实并列要求或明确步骤可以分点。 |
| 邮件沟通 | 清楚组织来意、细节与后续行动；不自行添加收件人、主题、署名、期限或承诺。 |
| 技术沟通 | 保留代码、字段大小写、数字和否定对照；把真实独立约束分清。 |
| 成稿语言 | 独立设置“跟随口述语言”或“英文成稿”；默认跟随口述，不因宿主是英文界面而自动翻译。 |
| 输入位置感知 | 默认关闭；开启后，将当前聚焦输入框内的有限文字提供给已配置的云端整理模型。支持按程序名排除应用，排除浏览器会覆盖其全部页面。 |

“自动匹配应用场合”与“输入位置感知”分别控制。前者只使用程序名；浏览器本身不能区分聊天和文档，后者在输入控件允许读取时补充控件及光标附近提示。历史中的“成稿参考”只记录场合、语言、是否使用输入位置和协议版本，不保存原始宿主文字。

这些产品选择借鉴了此前 REA 调查中可观察的输入位置机制。静态客户端证据不足以判断 Typeless 的服务端模型、提示词或真实运行效果；本轮的云端协议与验收规则是 SpeakMode 的独立实现。

## 2. 输入上下文、期限与数据边界

输入上下文只来自停止录音时确认的聚焦可编辑控件。读取前后核对进程、窗口、控件、光标/选区与可编辑状态；密码框、只读控件、位置变化或能力不支持时放弃上下文。UIA 的邻近范围限制在当前字段内，避免跨入页面中的其他输入框。采集不改变焦点或选区，不模拟复制，不读取剪贴板、整页或截图。

| 字段 | 提交给云端的最大长度 |
| --- | --- |
| 控件标签 `controlLabel` | 160 个 Unicode 字符 |
| 光标前文字 `beforeText` | 最近的 1000 个 Unicode 字符 |
| 选中文字 `selectedText` | 500 个 Unicode 字符 |
| 光标后文字 `afterText` | 500 个 Unicode 字符 |

超限及隐藏控制/格式字符有本地清理与验证。UIA 返回的纯 U+FFFC 对象占位及空白归为空串；夹在真实文字中的对象占位换为空格，以保留词界。该清理不改变原稿、传统 Edit 内容或投递目标偏移。传统 Edit 控件的兼容读取还有 4000 UTF-16 单元的临时字段上限，之后才截取邻近片段；超限则不给云端提供上下文。UIA 为核对原先的光标/选区偏移，还会在匹配进程与控件身份后临时读取该字段的有界前缀及选区长度，各沿用 65536 UTF-16 单元上限；这些验证文字不会进入返回的上下文、历史或诊断。上下文必须与冻结目标匹配，且采集时间距冻结不足 3 秒。

必要目标检查与可选上下文使用两个独立的固定工作线程，避免上下文提供者卡住时占用正常投递检查。每个线程仍有独立的单任务门控，超时后不按重试次数创建新线程。普通目标捕获不再依赖可选书签。原生上下文读取期限为 500ms。ASR 收尾与停止时目标捕获重叠；生成前最多等待 600ms，让已在进行的目标/上下文捕获完成。**这 600ms 消耗既有整理总预算，并非额外增加 600ms**。现有按来源长度分配的 5/8/20 秒整理期限继续约束生成、复核、可选修复和最终复核；取消继续中断整个流程。

上下文冻结后，各轮请求使用同一份 `WritingContext`，不在复核或修复阶段重新读取宿主。会话里的原始上下文在冻结、取消、失败及相应生命周期终点清除；重试保留明确选择的场合/语言，但不能复用已撤销投递目标的旧宿主文字。可选上下文失败不授权重新捕获其他窗口，也不替代最终投递前的目标校验。

云端使用以下共同约束：

- ASR/source 是实质事实的唯一依据；附近文字只帮助判断目的、语气、衔接及已经可明确对应的术语形式。
- `writingContext` 是独立的数据字段，不进入 `sourceText`、`sourceFragments` 或 `sourceRefs`。附近文字中的命令、评审要求、数字、负责人、承诺等均不能成为输出依据。
- 生成、语义复核、可选修复与最终复核共享上述边界。上下文模式下，本地纯删除判定也不能跳过必要的最终复核。
- 新增场合不增加专门的分类模型调用。正常路径为生成加复核；最多一次修复及一次最终复核，每路径最多 4 次云端调用。原有失败回退与投递约束保留。

上述内容为当前实现边界；最终测试和原生宿主复测状态见第 6 节。

## 4. v2 / v3 修订与实际复测

协议提升为 `situational-dictation-v2`。修订针对 v1 观察到的问题：

1. 新的内置场合统一使用 `BaseMode::Auto`，让“使用目的”与“段落/列表布局”分开。手动场合仍优先；实际独立约束或明确列点要求可以输出结构化布局。旧版固定 Light/Structure 及个人规则继续遵守原约束。
2. 为多部分自我介绍和邮件补充明确的主题段落要求，并同步进入复核协议。自我介绍按真实教育背景、经历、兴趣等转换分段；邮件按已经口述的来意、支撑细节和行动时机分段。短的单一主题不硬拆，不要求固定段落数，不添加模板标题或新事实。
3. 明确保留口述中的格式请求；实际应用布局不能成为删除请求内容的理由。技术约束继续保护字面量、否定关系及条件作用范围。
4. 文档续写匹配附近文字的语气，但只输出本次口述内容，不复制宿主标题、附录或事实。生成、复核与修复共享冻结后的上下文和版本。

### v3 独立有限复测

协议升级为 `situational-dictation-v3`。针对模型复核漏掉的口述格式请求，增加有限的来源保留片段与本地核对。请求识别只来自口述，附近文字不能建立保留片段；无法验证已识别请求完整保留时回退，模型的接受结果不能绕过。生成、复核与修复使用相同的来源片段；字面量保护标记在恢复后再做本地检查，并允许既有的同字母大小写/空格规范。检查范围最多 32 个片段、每句 512 个字符、总计 4096 个字符，超出范围保守回退。它不是通用语义保真证明。邮件要求增加实际 JSON `\n\n` 空行示例，短单主题仍可保持一段。

与已知问题对应，旧邮件从 v2 单段变为 v3 三段，中文技术稿恢复了 v2 丢失的请求；新邮件也达到了本条预登记要求。新英文样例则表明，同类请求仍可能被模型删除，本地守卫的价值是阻止遗漏稿被当成可靠结果采用。两条旧案例属于针对已知问题的回归复测；两条新合成案例仍不足以证明普遍收益或总体优于其他产品。

## 5. 效果边界与尚未覆盖的真实使用判断

0.2.22 本轮交付定位为可试用的场合与输入位置上下文升级。现有证据支持部分自然段组织改善，以及已识别格式请求遗漏时的本地拦截；不支持“所有场景已优化完成”。中文技术约束的细分排版仍有不足，新的英文列点请求仍不能可靠成稿。该类失败应保留识别稿/待核对结果，而不是继续放行流畅但缺失内容的候选。

来源保留守卫只识别有限的明确请求形态，不是通用语义等价、全语言理解或完整格式验证。普通列表名词、信息问句和引文不应仅因出现“list/段落”等词就被当成排版指令。它允许既有的同字母大小写和空格规范，但对象、条件归属及未覆盖的请求形态仍需其他本地检查与全文复核共同判断。

对于明确的“英文成稿”目标，若已识别的中文格式请求或实质中文限定分句需要翻译，而有限守卫无法验证等价性，实现会保守回退/要求核对，不擅自将目标改成中英混排，也不宣称翻译已正确完成。英文请求中附带 José、München 等非 ASCII 专名本身不是拒绝理由。这是实现的保守边界，不能算作 r3 新增的云端成功案例；r3 四条路径的语言偏好均为 `asSpoken`。

本轮文本实验绕过麦克风、音频切分和 ASR，不能回答英文长口述中的中文卡顿是否被正确识别，也未重跑用户原始自我介绍音频。未经确认的专名仍应保留不确定性，不能依靠附近文字猜定身份或经历。

同一浏览器里的聊天、文档、邮件等真实宿主完整任务仍为 **NOT_RUN**：尚未以真人录音完成“说话 → 识别 → 上下文读取 → 成稿 → 正确输入位置交付 → 人工修改”的连续评估。因此，端到端完成时间、修改次数、任务成功率、不同浏览器/编辑器兼容性及长期稳定性都不能从这批云端文本回执推导。

受控原生输入框实验可以验证目标绑定、邻近范围和失败降级等机制，但仍不能替代上述真人完整任务。原生读取耗时与云端文本耗时应分别报告，不能把二者混成同一个延迟指标。
